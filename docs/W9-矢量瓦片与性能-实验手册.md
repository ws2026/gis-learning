## 0. 本周要建立的三个认知

| # | 认知 | 为什么重要 |
| --- | --- | --- |
| 1 | **矢量瓦片 = 预切好的"数据罐头"**：像 WMTS 一样 URL 即缓存键、可上 CDN，但罐頭里装的是几何+属性而不是像素，样式和交互仍在前端 | W8 两个骨架的短板（WMS 不能点、WFS 太大卡）它都绕开；面试选型题"WMS/WFS/MVT 区别与取舍"（主计划面试题 3）的标准答案 |

## 1. 学（约 4~5 小时，周一到周三）

### 1.1 为什么 100 万点必须切片（0.5 h，把 W3 结论用到数据上）

**学完你能做什么**：向任何人讲清"100 万点直接进浏览器会卡在哪三座山上"，以及矢量瓦片如何把数据量问题变成缓存问题。

W3 实测过：一屏瓦片请求数随 z 约 ×4 增长——**视野决定了"该给用户看多少东西"**。图片瓦片把这道理用在"贴图"上，矢量瓦片用在"喂数据"上：

- 100 万点直接 GeoJSON 进浏览器：几十上百 MB 文本 → JSON 解析 → 100 万个 `Feature` 对象 → 每帧 Canvas 重绘。首屏几十秒起步，拖动个位数帧率。**卡的原因不是网络一条，是"解析、对象化、重绘"三座山**。
- 切成 MVT 后：z=5 视野内可能只有 2 万个点的抽样、每屏 20~40 个 `.pbf` 请求（gzip 后各几 KB），前端只实例化**视野内的**。缩放=换一层罐头，拖动=补边缘罐头——和 W3 的瓦片调度完全同构。
- 一句话：**矢量瓦片把"数据量问题"转换成"缓存与编号问题"**，而编号问题 Web 早就解决了。

概念四件套 · **矢量瓦片（MVT）**：定义——把矢量数据按瓦片金字塔预切成二进制小块（`.pbf`）的格式；类比——罐装水果 vs 现摘果树：罐头（切片）开盖即食、可囤货（CDN 缓存），但内容固定在生产那天；最小示例——`http://127.0.0.1:3000/points_1m/12/3336/1777.pbf` 就是 z12 的一块罐头；常见误区——以为 MVT 是"图片的一种"，其实它是**数据**（可在前端换样式、点击查询），图片瓦片才是像素。

### 1.2 tippecanoe：切片器逐参数精讲（1 h）

**学完你能做什么**：在 Windows 上把 tippecanoe 装好并验证成功；看懂并手调一条切片命令的每个参数；说出 `--drop-densest-as-needed` 的收益与代价。

tippecanoe 是 Mapbox 出品的命令行切片器：喂 GeoJSON（流式，百万点也不怕内存），吐 `.mbtiles`。概念四件套：定义——GeoJSON→瓦片金字塔的离线切片器；类比——食品加工厂的"罐头生产线"，原料（GeoJSON）进去，按层装罐；最小示例——下方最小命令；常见误区——以为它能在 Windows 原生直接跑（不能，坑 P1），以为 `-z` 写死就不会被突破（`--extend-zooms-if-still-dropping` 会突破）。

**先装**（二选一，两条路线都给逐步流程）：

**路线 A（推荐）：WSL apt 安装**

```bash

sudo apt update                                   # 预期输出：拉取软件源列表，结尾无 Err
sudo apt install -y tippecanoe                    # 预期输出：Setting up tippecanoe ...
tippecanoe --version                              # 预期输出：tippecanoe v2.x.x（有版本号即成功）
# 失败时：apt 源里没有或版本太旧 → 源码编译：
# sudo apt install -y git build-essential libsqlite3-dev zlib1g-dev
# git clone https://github.com/felt/tippecanoe.git && cd tippecanoe && make -j && sudo make install
# 仍失败 → 坑 P1，或改走路线 B
```

**路线 B：conda-forge（Windows 原生，免开 WSL）**

```powershell
# 【PowerShell】注意装进 webgis 环境，GDAL 依赖会被一并带进来（被动依赖，别和 W2"不要 conda 装 GDAL"搞混）

```

最小命令 + 参数表（在【WSL bash】跑；文件路径 WSL 里是 `/mnt/d/...`，这是坑 P4）：

```bash
tippecanoe -o points1m.pmtiles -Z0 -z14 --maximum-zoom-detail=15 \
  -zg --drop-densest-as-needed --extend-zooms-if-still-dropping \
  --no-feature-id -l points \
  /mnt/d/xx/GitProjects/gis-learning/projects/tileperf-lab/data/points_1m.geojson.ndjson
```

**预期输出**：逐层打印瓦片统计；稠密层出现 `Dropping ...% of features at zoom ...` 字样（删点证据，练习 1 要抄进笔记）。**失败时**：报 `No such file` → 路径写法坑 P4；报内存不足 → 确认喂的是 NDJSON 而非单个 100MB GeoJSON。

| 参数 | 在干什么 | 代价/注意 |
| --- | --- | --- |
| `-Z0`（大写） | **最高**缩放层：金字塔顶。定 0 表示从全球一张切起 | 顶设太高（如 `-Z20`）低层白切一堆空瓦片、体积爆炸 |
| `-z14`（小写） | **最低**（最详细）层：切到 14 级为止，15+ 级由前端把 14 级瓦片放大顶住（W3 的 overzoom） | 层数越少体积越小，但放大后细节糊；点数据一般 13~15 够用 |
| `-zg` | 自动决定"最详细层"：按数据密度挑一个让最底层不过度拥挤的 z | 与手写 `-z` 二选一；结果不可预测于面试解释，理解期建议先手调再对比 `-zg` |
| `--drop-densest-as-needed` | **核心魔法**：若某层切片后仍然太大（默认目标 500KB/层附近），就**从最稠密的瓦片里删点**，直到达标 | 代价：小比例尺下看到的是**抽样**——用它做的地图"数点数"会数错；需要统计请查库（W7）或到点足够详细的层级。验收项 2 考的就是这句 |
| `--extend-zooms-if-still-dropping` | 若删无可删还是超标，**往下多切一级**而不是继续删 | 体积换保真——知道这个开关，才能解释 `-z` 会被自动突破 |
| `--simplify` 系列 | 对线/面按道格拉斯-普克抽稀顶点（如 `--simplify-at-radius -r 50`）；对点等效手段是 drop | 简化改变形状（W2 就讲过"精度换体积"，同一决策在瓦片层重演）；点数实验用不到，政区层 `gz_districts` 你会见到顶点明显变少 |
| `-l points` | 图层命名（前端 style 里按名引用） | 不指定时取自输入文件名 |
| `--no-feature-id` | 不生成要素 id | 省体积；但前端就没法按 id 定位要素——练习里不需要 id |
| `-o xxx.pmtiles` / `.mbtiles` | 输出单文件包 | 换后缀即换格式（`-f mbtiles` 显式指定） |

产出 `.mbtiles` 是什么？下一节拆开看——**这是本周最涨姿势的三分钟**。

### 1.3 .mbtiles 的真相：一张 SQLite 表（0.5 h）

**学完你能做什么**：用一条 SQL 把 mbtiles 的分层瓦片数/体积统计出来，讲出"哪级最肥、低层为什么几乎空"。

`.mbtiles` 就是一个 SQLite 数据库文件（W2 学过 GPKG 同样是 SQLite——GDAL 家族都爱拿 SQLite 当容器）。概念四件套：定义——用 SQLite 存的瓦片包；类比——Excel 文件里其实可以塞很多张表，mbtiles 里就塞了 `metadata` 和 `tiles` 两张；最小示例——下面的 `.tables`；常见误区——以为它是 Mapbox 私有黑盒格式，其实任何 SQLite 工具都能打开。

【PowerShell】装个 `sqlite3` 或用 QGIS 浏览器面板直接点开也行；命令行党：

```bash
# 【WSL bash】sqlite3 没装就 sudo apt install -y sqlite3
sqlite3 /mnt/d/xx/GitProjects/gis-learning/projects/tileperf-lab/data/points_1m.mbtiles
```

【sqlite3 交互】里：

```sql
.tables                                              -- 预期：metadata  tiles
SELECT zoom_level, tile_matrix_width FROM metadata;  -- 层级范围等元信息
-- 关键一条：每级多少瓦片、平均/最大多大
SELECT zoom_level, count(*) AS tiles,
       avg(length(tile_data)) AS avg_bytes,
       max(length(tile_data)) AS max_bytes
FROM tiles GROUP BY zoom_level ORDER BY zoom_level;
```

**预期现象**：三列数字讲出金字塔的故事——z0 只有 1 行、z1 最多 4 行、每级 ×4（W3 公式回收）；`tile_data` 就是 `.pbf` 字节，所以 `length(tile_data)` 即压缩前瓦片体积；低层级 avg 几十字节（几乎空）、中层最肥。`WHERE zoom_level=12 AND tile_column=3336 AND tile_row=1777` 能捞出你 W1 背下来的那块广州瓦片——**四方交叉验证老朋友第五次出场**。这一眼看完，"瓦片服务"的神秘感清零：所谓服务器，就是替你把这条 SELECT 的 BLOB 用 HTTP 发出来。**失败时**：sqlite3 打不开文件 → 确认切片成功产物存在；路径问题 → 坑 P4。

### 1.4 瓦片服务器三选一：tileserver-gl / Martin / pg_tileserv（1 h）

**学完你能做什么**：按决策树 30 秒选出适合自己数据形态的服务器，并用一条命令把 Martin 起起来。

概念四件套 · **瓦片服务器**：定义——把"瓦片编号 z/x/y → 瓦片字节"这条查询用 HTTP 暴露出来的服务；类比——自动售货机：你按编号（URL），它吐货（pbf）；最小示例——`http://127.0.0.1:3000/points_1m/12/3336/1777.pbf`；常见误区——以为瓦片服务器会"渲染样式"，文件模式它只发数据，样式在前端（1.5）。

**决策树**（按你的数据形态选）：

```
你的数据在哪、怎么变？
├─ 在 PostGIS 里，且经常更新（改一条就要前端看得见）
│   → pg_tileserv（扩展直挂 pgis，SQL 建视图即出瓦片）
│     或 Martin 库模式（Rust 单文件，实时切片，性能更好）
├─ 是静态切片文件（mbtiles/pmtiles），更新频率低（重切可接受）
│   → Martin 文件模式（本周主线，一条命令起）
└─ 要"一键全站底图+整套样式"（OpenMapTiles 类）
    → tileserver-gl（自带 style.json 渲染，但 Windows 原生安装有坑 P2）
```

详细对比表：

| 维度 | **tileserver-gl** | **Martin（本周推荐）** | **pg_tileserv** |
| --- | --- | --- | --- |
| 吃什么数据 | style.json + pmtiles/mbtiles 打包的**整套样式** | mbtiles/pmtiles 文件，**或**直连 PostGIS 表实时生成 MVT | **只**直连 PostGIS 表（函数式，SQL 里建视图即出瓦片） |
| 数据更新需求 | 切片后是**快照**：库改了要重切重灌 | 文件模式=快照；**数据库模式=实时**（每请求现查现切） | 永远实时：`UPDATE schools ...` 下一请求就变（与 W8 的"改一条数据看得见"同性质） |
| 技术栈 | Node（npm 安装，Windows 原生编译有坑，见下） | 单个 Rust 可执行文件，免运行时 | PostgreSQL 扩展（`CREATE EXTENSION postgis_tileserv`），搭在已有 pgis 上 |
| 上手难度 | 中：还要伺候 style.json | 低：一条命令起，URL 直出 `{z}/{x}/{y}.pbf` | 低~中：装扩展 + 建 schema 权限 + 瓦片几何列约定 |
| 附带能力 | 自带 MapLibre 样式渲染/静态图/栅格 | 纯瓦片 HTTP 服务 + 漂亮性能（内置连接池） | 纯瓦片；过滤条件可以写进视图 SQL |
| 典型场景 | 要"一键全站底图"（OpenMapTiles 类） | 学习、中小规模通吃 | **数据在 PostGIS 且要求前端样式可换**——最贴合你阶段三系统的形态 |

选型口诀：**数据在库里常更新 → pg_tileserv（或 Martin 库模式）；数据是静态切片 → 文件 + Martin/tileserver-gl。** 本周主线走 **Martin**（文件模式起步，库模式当加练）；pg_tileserv 用你现成的 pgis 十分钟能试出味道。

**npm 装 tileserver-gl 的 Windows 坑（预告坑 P2）**：`npm install -g tileserver-gl` 在 Windows 上要编译原生依赖（better-sqlite3 等），没装 Visual Studio Build Tools 就一片红。绕法优先级：WSL 里装 > conda-forge `tileserver-gl-lite` 替代品 > 干脆用 Martin。**学习阶段工具服从目的**：目的"有个 pbf 端点"，Martin 一条命令就到。

Martin 起服务（【PowerShell】，exe 从 GitHub Release 下载；拉不动就 W0 笔记第六节：Steam++ hosts 加速先开着，坑 P5）：

```powershell
# 文件模式：把整个 data 目录挂成瓦片源
.\martin.exe D:\xx\GitProjects\gis-learning\projects\tileperf-lab\data --port 3000
# 库模式（加练）：实时切片
$env:DATABASE_URL='postgres://postgres:postgres@127.0.0.1:5432/gislab'
.\martin.exe --port 3000
```

**预期现象**：浏览器开 `http://127.0.0.1:3000` 列出源；文件模式点开某源 → `http://127.0.0.1:3000/points_1m/12/3336/1777.pbf` 下载回一个几 KB 的 pbf；库模式则是 `.../public.schools/12/3336/1777.pbf`（Martin 自动按表生成 MVT）。前端要用的 URL 模板：`http://127.0.0.1:3000/points_1m/{z}/{x}/{y}.pbf`。**失败时**：启动即退出 → 坑 P3（端口占用换 `--port 3001` 并同步改前端 URL）。

### 1.5 前端完整骨架：ol/source/VectorTile + MVT + style 函数（1 h）

**学完你能做什么**：用 20 行代码把 pbf 端点接上 OpenLayers 地图，并用 style 函数按属性控制每个要素画不画、怎么画。

OpenLayers 吃 MVT 三件套：`VectorTileSource`（取瓦片+解码）/ `MVT` 格式（解析 pbf）/ `VectorTileLayer` + style 函数（**前端管样式**，W5"样式与数据分离"兑现）。概念四件套 · **style 函数**：定义——每个要素渲染前被调用一次、返回样式或 null 的函数；类比——流水线上的质检员，逐个产品（要素）决定贴什么标签、要不要下架；最小示例——下面代码里按 `class` 判断那段；常见误区——以为返回 null 是"出错"，其实它是"属性裁剪"的正式手段。

```js
// 【webgis-starter 项目代码】如 web/mvt.js
import VectorTileLayer from 'ol/layer/VectorTile.js';
import VectorTileSource from 'ol/source/VectorTile.js';
import MVT from 'ol/format/MVT.js';
import { Style, Fill, Stroke, Circle } from 'ol/style.js';
import { fromLonLat } from 'ol/proj.js';

// MVT 瓦片坐标系固定 3857（W2 表格里的"瓦片方案定死 3857"）——这是最大认知陷阱：
// 几何坐标不是经纬度，而是"瓦片内 0~4096 格点 + 瓦片范围"推算出来的 3857 米值。
export function makePointsTileLayer(name = 'points_1m') {
  const src = new VectorTileSource({
    format: new MVT(),
    url: `http://127.0.0.1:3000/${name}/{z}/{x}/{y}.pbf`,
    maxZoom: 14,                      // 与切片最详细层对齐；之上 overzoom
  });
  src.on('error', (e) => console.warn('瓦片加载失败', e));   // 404 排查友好（坑 P7）

  const pointStyle = new Style({
    image: new Circle({ radius: 3, fill: new Fill({ color: '#d7301f99' }) }),
  });
  return new VectorTileLayer({
    source: src,
    style: (feature) => {             // ← style 函数：每个要素渲染前调用一次，按属性决定长相
      const c = feature.get('class'); // 属性过滤/分级都写在这里，W4 的技能平移
      if (c === '住宅') return pointStyle;
      return null;                    // 返回 null = 不画这个要素（视野裁剪之外再加"属性裁剪"）
    },
    declutter: true,                  // 标注/图标重叠避让（计划里点名的前端优化项）
  });
}
```

**预期现象**：`npm run dev` 后地图出现红色点云，Network 面板一串 `.pbf` 200 请求。**失败时**：全 404 → 坑 P7（源名/zoom 范围对不上）；全空白且无请求 → 图层没 add 进 map。

要点（改一处、说清为什么——本周纪律）：

- `declutter`：重叠要素/标注自动避让抽稀——**视觉减负不等于数据变少**，它治"糊成一团"，不治"卡"；治卡靠金字塔（1.2）。
- style 函数返回 `null` 跳过绘制：按属性动态显隐在瓦片渲染里能做，但注意要素对象是**每个瓦片解码出来的**，属性只有切片时带进去的那些（`-l`/字段选择决定，tippecanoe 默认全带上，可用 `--exclude` 减体积）。
- MVT 是**只读**几何：点不了"拾取绘制"，但 `layer.getFeaturesInfo`（新版）/ `forEachFeatureAtPixel` 点击查询照样能写——W8 WFS 弹窗的手感平移过来即可（选做挑战）。
- 分级简化、按需加载、按视野裁剪三件套在瓦片体系里是**白送**的（金字塔+瓦片调度+裁剪天然按视野），前端真正自己要做的只剩 style/declutter——这句话写进笔记，就是"为什么 MVT 快"的完整版。

### 1.6 性能实验怎么测才算数（1 h，本周严谨性担当）

**学完你能做什么**：按"实验前→测量中→记录表"三段流程跑出一组可复现的对照数字，并知道每个数字从哪个面板读。

概念四件套 · **控制变量**：定义——一次只改一个因素（渲染方式），其余全部锁死；类比——药店试新药要分实验组/对照组，两组病人其他条件一样；最小示例——下面"实验前"清单；常见误区——两次测试中间换了视野/开了新标签页，然后惊呼"快了 10 倍"（那是缓存，坑 P6）。

**控制变量三定**：同一台电脑（浏览器也开同样的标签页数，关掉别的）、**同一视野**（固定 center=广州塔、zoom 写死，两版代码用同一个 `view` 配置）、同一数据（同一份 100 万点；GeoJSON 直载版若嫌解析久可退到 20 万点，但表格里必须注明数据量——这就是控制变量的"诚实"）。

**实验前（每轮测试前照做一遍）**：

1. 两版页面（GeoJSON 直载 / MVT）的 `view` 配置**复制同一段代码**写死，例如：

   ```js
   // 【webgis-starter 项目代码】两版共用，别手敲两遍——手敲就会不一致
   const view = new View({ center: fromLonLat([113.2644, 23.1291]), zoom: 12 });
   ```

2. 打开 DevTools → Network 面板 → 勾 **Disable cache**（W3 坑 P2 的老教训，首屏测热缓存=自欺）。
3. 关闭无关标签页与后台大程序；每轮用 **Ctrl+Shift+R** 硬刷新。

**测量中（看这三个数字）**：

- **指标一 · 首屏时间（两层含义分开测）**：
  - 人话版"首屏"= **FCP（First Contentful Paint）**：Performance 面板 → 录制 → 顶部标尺上 `FCP` 标记；或 `main.js` 开头打一条 `console.time('boot')`、地图首个 `rendercomplete` 时 `console.timeEnd('boot')`——"自定义首屏"，测的是"我这地图真画完第一帧"，读数在 **Console** 面板看：

    ```js
    // 【项目代码】main.js 里
    console.time('map-boot');
    let firstFrame = false;
    map.once('rendercomplete', () => { console.timeEnd('map-boot'); firstFrame = true; });
    // 预期输出（Console）：map-boot: 1234.56 ms
    ```

  - 更硬的证据在 Network 面板：底部 `DOMContentLoaded` 时刻 + `Transfer Size` 总量——GeoJSON 直载的 40MB 与 MVT 的 ~10MB 一对比，首屏差距的根源一目了然。
- **指标二 · 拖动帧率（rAF 计数，现成可复制）**：把下面这段**整段贴进浏览器 DevTools 的 Console 面板**【浏览器 DevTools】（贴完回车，无输出即就绪），然后输 `startFps()` 回车 → 立刻匀速拖动地图 10 秒 → 输 `stopFps()` 看结果：

  ```js
  // fps-meter：requestAnimationFrame 计数法。原理：屏幕刷新由 rAF 驱动，
  // 渲染越重，rAF 回调间隔越大，测得的 fps 越低。
  window.__fps = { on: false, frames: 0, t0: 0, samples: [] };
  function fpsLoop(now) {
    if (!window.__fps.on) return;
    window.__fps.frames++;
    if (now - window.__fps.t0 >= 1000) {           // 每满 1 秒报一次
      const fps = (window.__fps.frames * 1000) / (now - window.__fps.t0);
      window.__fps.samples.push(Math.round(fps));
      console.log('fps:', Math.round(fps), '| 样本:', window.__fps.samples.join(','));
      window.__fps.frames = 0;
      window.__fps.t0 = now;
    }
    requestAnimationFrame(fpsLoop);
  }
  window.startFps = () => { window.__fps.on = true; window.__fps.samples = [];
    window.__fps.t0 = performance.now(); window.__fps.frames = 0; requestAnimationFrame(fpsLoop); };
  window.stopFps = () => { window.__fps.on = false;
    const s = window.__fps.samples; const min = Math.min(...s); const med = s.sort((a,b)=>a-b)[s.length>>1];
    console.log(`结束：最低 ${min} fps / 中位 ${med} fps / 全部 ${s.join(',')}`);
    return s; };
  // 用法：startFps() → 匀速拖动地图 10 秒 → stopFps()；把"中位/最低"两个数记进表格
  // 预期输出：每秒一行 fps: 45 | 样本: ...，结束时一行"最低 32 fps / 中位 44 fps ..."
  // 失败时：贴进去报 SyntaxError → 检查是否漏贴首行或中文括号混入（W0 坑 #9 同类）
  ```

**记录表模板**（直接复制到报告里填；同一变量至少测 **3 轮取中位**——单次波动 ±10 fps 很正常，坑 P8）：

```markdown
| 指标（冷缓存，Disable cache 已勾） | GeoJSON 直载 | 矢量瓦片 MVT |
| --- | --- | --- |
| 测试条件（机器/浏览器/视野中心/zoom/数据量/轮数） | 例：i5/Chrome 131/广州塔/z12/100万点/3轮取中位 | 同左 |
| 传输总量 (Transfer Size) | | |
| 自定义 boot (ms) | | |
| FCP (ms) | | |
| 拖动 fps 中位 / 最低 | | |
| 拖动时 CPU 热力图尖峰（Performance 选看） | | |
```

**读数口径**（写进报告，免得自己跟自己打架）：fps 看**拖动期间的中位数与最低值**，别看最高（空闲时它就是 60）；"不明显卡顿"的过关线取 **中位 ≥ 30、最低 ≥ 20**（学习口径，非国标）。

```python
cls = rng.choice(['住宅', '商业', '工业'], n)
# MVT 切片喂 NDJSON（每行一个 feature）最快最省内存，tippecanoe 原生支持
with open('points_1m.geojson.ndjson', 'w', encoding='utf-8') as f:
    for i in range(n):
        f.write(json.dumps({"type": "Feature",
            "geometry": {"type": "Point", "coordinates": [round(float(lon[i]), 6), round(float(lat[i]), 6)]},
            "properties": {"id": i, "class": str(cls[i])}}) + '\n')
print('done', n)
```

Node 版备选（无第三方依赖，练流式写）：

```js
// gen-points.mjs —【PowerShell】node gen-points.mjs（Node v22+；n 同样先 10_000 试跑）
import { createWriteStream } from 'node:fs';
const n = 10_000, out = createWriteStream('points_1m.geojson.ndjson', { encoding: 'utf8' });
// 简易可复现正态（中值定理法，够用且跨平台稳定）
function normal(mu, sigma) { let s = 0; for (let i = 0; i < 12; i++) s += Math.random(); return mu + (s - 6) * sigma / Math.SQRT2 * Math.sqrt(3); }
// 注意：上面近似有缩放偏差，学习期无妨；要精确就用 numpy 版。
let buf = [];
for (let i = 0; i < n; i++) {
  buf.push(JSON.stringify({ type: 'Feature',
    geometry: { type: 'Point', coordinates: [+(113.26 + normal(0, 0.08)).toFixed(6), +(23.13 + normal(0, 0.06)).toFixed(6)] },
    properties: { id: i, class: ['住宅', '商业', '工业'][Math.floor(Math.random() * 3)] } }) + '\n');
  if (buf.length >= 10_000) { out.write(buf.join('')); buf = []; }   // 分批写：逐行 await 写会慢一个数量级
}
if (buf.length) out.write(buf.join(''));
out.end(() => console.log('done', n));
```
