## 1. 学（约 4 小时，分散在周一到周三）

### 1.1 三个坐标系对照表（抄进笔记，抄的过程就是记）

> **学完你能做什么**：看到任何一串坐标数值（113.26/23.12 还是 12608535/2647638），你能立刻判断它大概率是什么坐标系、单位是度还是米、该不该直接拿来算距离。

先给"坐标参考系（CRS）"四件套：

- **定义（一句话）**：CRS = 一套"用数字描述地球表面位置"的约定，包含基准椭球 + 原点 + 单位 + （投影系还有）投影公式。
- **类比**：像报地址——"东经 113.26°"是按经纬度门牌报，"往东 12,608,535 米"是按某张平面地图的方格报。同一个地方，报法不同数字完全不同。
- **最小示例**：【QGIS 界面→右下角状态栏】鼠标在地图上移动，状态栏实时显示光标坐标；切工程 CRS（`工程 → 属性 → 坐标参考系`），同一个位置数字会从 `113.26, 23.12` 变成 `12608535, 2647638`——点的位置没变，变的只是"报法"。
- **常见误区**：① 以为"坐标就是坐标，数字对了就行"——不带 CRS 的数字毫无意义（W1 三类原因之"身份错"）；② 以为 4326 和 3857 可以互相换算所以随便用——单位不同，算距离面积天差地别；③ 以为 EPSG 编号要背——不用背，会看 WKT 首词（GEOGCS/PROJCS）更可靠。

| 代号 | 全称 | 类型 | 单位 | 原点/基准 | 用在哪 | 一句话 |
| --- | --- | --- | --- | --- | --- | --- |
| `EPSG:4326` | WGS 84 地理坐标系 | 地理（GEOGCS） | **度** | Greenwich 本初子午线，椭球 WGS84 | GPS 原始值、GeoJSON 默认、数据交换、接口 | "经纬度"，全世界通用 |
| `EPSG:3857` | WGS 84 / Pseudo-Mercator（伪墨卡托） | 投影（PROJCS） | **米**（名义） | 几内亚湾 (0°,0°) | 几乎所有 Web 底图与瓦片方案、前端渲染 | "把世界拍平成一张正方形画布" |
| `EPSG:4490` | CGCS2000 地理坐标系 | 地理（GEOGCS） | **度** | 国家大地原点，椭球 CGCS2000 | 中国境内正式测绘/政务成果**法定**坐标系 | 数值与 4326 在本项目精度下**完全一致** |

几个必须能解释的说法：

- **Pseudo（伪）**：3857 的 PROJ 参数是 `+a=6378137 +b=6378137`——把长半轴当短半轴用，即**把椭球当正球**。这是它高纬放大的根本原因，也是它计算便宜、能全局铺瓦片的原因。
- **4490 与 4326 用 PROJ 互转结果相同**（椭球扁率倒数只差第 8 位小数），但**中国境内正式成果法律上必须用 CGCS2000**。这是合规问题，不是精度问题。
- **WKT 首词一眼判类型**：`GEOGCS`/`GEOGCRS` = 地理（度），`PROJCS`/`PROJCRS` = 投影（米）。在 QGIS 的 `工程属性 → 坐标参考系` 右侧 WKT 框里看首词，比记 EPSG 号可靠。
- **墨卡托有纬度上限 ±85.051°**：`atan(sinh(π))` 的度数。超过它 y 趋于无穷，所以 Web 地图不画南北纬 85.05° 以上的高纬地区。

### 1.2 GCJ-02 与 BD-09：为什么国内底图"故意对不上"

> **学完你能做什么**：拿到一份国内来源的坐标数据，你能说出它可能是哪种坐标、偏多少、怎么验证、怎么修。

四件套（以 GCJ-02 为例）：

- **定义（一句话）**：GCJ-02 是中国法定的坐标加偏算法：把真实 WGS84 经纬度用一个非线性公式"打乱"后发布，俗称火星坐标。
- **类比**：像官方发行的地图都经过同一个"哈哈镜"，镜子里各图（高德/腾讯）彼此能对上，但你拿真实世界的尺子（GPS/WGS84）去量镜子，处处差几百米。
- **最小示例**：【Anaconda Prompt】`conda activate webgis` 后 `python projects/coordinate-lab/w1_proj.py offset`，直接打印北京/广州/上海等城市的偏移量（367~724 m）。
- **常见误区**：① 以为偏移是固定值可以减一个常量修掉——它随位置变化；② 以为 PostGIS 的 `ST_Transform` 能转——`spatial_ref_sys` 里根本没有 GCJ-02；③ 以为"差不多能对上"就可以上线——z=18 级别下几百米偏移肉眼明显。

| 名称 | 谁在用 | 本质 | 与 WGS84 的偏差 | 表现 |
| --- | --- | --- | --- | --- |
| `GCJ-02`（火星坐标） | 高德、腾讯、阿里 DataV 部分数据 | 国家法定的**非线性保密偏移**：对 WGS84 经纬度做一次加偏变换 | 数百米级（本仓库实测 367~724 m，随位置变化） | 拿 WGS84 的点叠到高德底图上，整体偏移，形状正常 |
| `BD-09` | 百度 | 在 GCJ-02 之上**再偏移一次** | 比 GCJ-02 更大 | 高德坐标叠百度底图，也对不上 |

三个关键推论（本仓库已实测验证）：

1. 偏移**随位置变化**，所以**不能**用一个固定常量去减；
2. 偏移**是非线性的**，必须用算法转换（`w1_proj.py` 里有 `wgs84_to_gcj02` 与迭代反算 `gcj02_to_wgs84`）；
3. **PostGIS 里没有 GCJ-02 定义**（`spatial_ref_sys` 查不到，见 [coordinate.sql 第 6 节](../projects/coordinate-lab/sql/coordinate.sql)），所以 `ST_Transform` 转不了它——这是常见误区。

**合规习惯**：底图用天地图（CGCS2000，接近 WGS84）等正规来源并注意审图号；不要拿高德/百度瓦片直接上线商用。

### 1.3 XYZ 瓦片公式：逐项推导（对齐 [coord.mjs](../projects/coordinate-lab/coord.mjs)）

> **学完你能做什么**：给你任意经纬度和级别 z，你能用纸笔（或计算器）算出它在哪块瓦片上；在 Network 面板看到 `12/3336/1777.png` 能反推出大概位置。

四件套：

- **定义（一句话）**：XYZ 瓦片方案 = 把 Web 墨卡托世界按 z 级切成 `2^z × 2^z` 的方格，每个格子一张 256×256 图，用 `z/x/y` 三个整数编号。
- **类比**：像酒店房间号 `12/3336/1777`：12 楼（级别 z），第 3336 列（x），第 1777 行（y）。楼层越高（z 越大）房间越多、每间越小。
- **最小示例**：【PowerShell】`node projects/coordinate-lab/coord.mjs tile`，直接打印 z=1/2 的逐步手算过程和 z=12/15/18 的编号。
- **常见误区**：① 以为 x/y 可以互换——Esri 等服务的 URL 是 `{z}/{y}/{x}`，写反直接 404 或错位；② 以为 y 从下往上数——slippy map 的 y 从**顶部**开始（TMS 才从底部）；③ 以为 z 可以无限大——免费底图多数只到 z=19。

**先建立画面**：把世界切成 256×256 像素的方块，就像把一张世界地图裁成橘子瓣形状的拼图块。`z`（zoom，级别）决定裁成多少块：`z=0` 全世界 1 张，`z=1` 变成 2×2=4 张，`z` 每加 1，总数 ×4。`x` 是从左往右第几列，`y` 是从上往下第几行。

Web 墨卡托切片方案（Google / OSM / 天地图 w / 高德通用，叫 **slippy map**，y 轴向下）公式：

```
n  = 2^z
x  = floor( (lon + 180) / 360 · n )
y  = floor( (1 - asinh(tan(lat_rad)) / π) / 2 · n )
```

**每一项在干什么（验收项 1 要你逐条解释）**：

| 项 | 作用 | 大白话 |
| --- | --- | --- |
| `n = 2^z` | 该级每边瓦片数 | 级别越高，网格越密；z=1 每边 2 块，z=2 每边 4 块 |
| `(lon + 180) / 360` | 经度 -180~180 → 0~1 | 把"东西方向的位置"变成一个百分比 |
| `× n` 再 `floor` | 百分比 → 第几列 | 百分比乘以列数，向下取整就是列号 |
| `asinh(tan(lat))` | 纬度的墨卡托非线性变换 | 纬度不是线性铺开的，越往高纬"占的像素越多"；等价写法 `ln(tan(π/4 + lat/2))`，用 `asinh` 形式可避免 lat→±90° 时 tan 溢出 |
| `/ π` | 归一化到 -1~1 | 墨卡托 y 的范围是 ±π |
| `1 - ...` 再 `/ 2` | 翻转成"从上往下数" | 数学里 y 向上为正，瓦片 y 向下（0 在顶部，北半球在上），所以要 `1 -` |
| 外层 `floor` | 取整得索引 | 落在第几块里，就是几号 |

**手算示范（广州 113.2644, 23.1291）**：

```
z=1: n=2
     x = (113.2644 + 180) / 360 × 2 = 1.6292 → 1
     y = (1 - asinh(tan(23.1291°)) / π) / 2 × 2 = 0.8679 → 0
     结论：瓦片 1/0
z=2: n=4
     x = (113.2644 + 180) / 360 × 4 = 3.2585 → 3
     y = (1 - asinh(tan(23.1291°)) / π) / 2 × 4 = 1.7357 → 1
     结论：瓦片 3/1
```

`coord.mjs` 的 `tile` 子命令会把这些中间步骤打印出来，对照着核对一遍即可。
基准表（W0 已用 Network 面板见过 3336/1777）：

| z | 瓦片 x | 瓦片 y | 该级瓦片总数 |
| --- | --- | --- | --- |
| 1 | 1 | 0 | 4 |
| 2 | 3 | 1 | 16 |
| 12 | 3336 | 1777 | 16,777,216 |
| 15 | 26693 | 14219 | 1,073,741,824 |
| 18 | 213548 | 113752 | 68,719,476,736 |

反算（编号 → 该瓦片覆盖的经纬度范围）用 `tileBounds()`，作用是**自证**：算出的 bbox 里必须包含原始点，否则编号写错了。

> **y 方向有三套约定**，这是花屏/404 的高频原因：slippy（y 向下，本手册与 `coord.mjs`）、**TMS**（y 向上，转换 `y_tms = 2^z − 1 − y`）、ArcGIS REST 的 URL 顺序是 `{z}/{y}/{x}`（[basemaps.js](../projects/webgis-starter/src/basemaps.js) 第 69 行就是它）。

### 1.4 pyproj 的 Transformer：怎么用（Python，Anaconda Prompt）

> **学完你能做什么**：能用 4 行 Python 把任意点从 4326 转到 3857 再转回来，并且知道 `always_xy=True` 不写会踩什么坑。

四件套：

- **定义（一句话）**：`Transformer` 是 pyproj 里"从 CRS A 到 CRS B 的坐标转换器"，建一次可以反复用，还能反算。
- **类比**：像办一张固定线路的换乘卡（"4326 → 3857"），刷卡就换；`always_xy=True` 相当于在卡上注明"我永远先报经度"。
- **常见误区**：① 用旧教程的 `pyproj.transform()`（不传 `always_xy`）——轴序按官方定义走，lat/lon 反了都不知道；② 以为 CRS 写法无所谓——`EPSG:4326`、`4326`、`"OGC:CRS84"` 含义可能不同，**统一写 `EPSG:xxxx`**；③ 以为转换结果会因库不同而不同——坐标转换是封闭公式，标准实现结果必须一致（四方交叉验证误差 0）。

**为什么用 `Transformer` 而不是 `pyproj.itrf()`（旧写法）**：`Transformer` 明确指定"从哪个 CRS 到哪个 CRS、是否先归一化为 xy 轴序"，可读、可复现，还能一步算出用了哪条转换路径。

```python
# projects/coordinate-lab/w1_proj.py 的最小可用片段（在 Anaconda Prompt 里跑）
from pyproj import CRS, Transformer, TransformerGroup

# 1) 建转换器：4326 -> 3857，always_xy=True 强制"经度在前"（lon, lat）
#    不加它，某些 CRS 会按官方轴序（lat, lon）解释，这是坐标错位第一大来源
tf = Transformer.from_crs(CRS("EPSG:4326"), CRS("EPSG:3857"), always_xy=True)

x, y = tf.transform(113.2644, 23.1291)      # 正算
print(f"x_3857 = {x:.2f}, y_3857 = {y:.2f}")  # 期望 12608535.33 / 2647638.58

lon, lat = tf.transform(x, y, direction="inverse")   # 反算（同一对象可逆）
print(f"back = {lon:.9f}, {lat:.9f}")                 # 应回到原值，误差毫米级

# 2) 4326 -> 4490：结果与直接返回相同数值（本仓库实测一致）
tf2 = Transformer.from_crs(4326, 4490, always_xy=True)
print(tf2.transform(113.2644, 23.1291))

# 3) 看"它到底用了哪条转换路径"（多版本/带网格的转换会有多条候选）
group = TransformerGroup(4326, 4490, always_xy=True)
for t in group.transformers:
    print(t.description)
# 4) 距离/面积要椭球计算时用地理坐标系或显式椭球，不要在 3857 里算（见 1.5）
print(CRS("EPSG:3857").is_geographic, CRS("EPSG:3857").axis_info)
```

- **预期输出**：第 1 段打印 `x_3857 = 12608535.33, y_3857 = 2647638.58`，往返误差显示 `≈ 0.000xxx 毫米`；第 2 段打印 `(113.2644, 23.1291)` 原值；第 3 段打印若干行转换路径描述；第 4 段打印 `False` 和两条轴信息。
- **失败时**：`ModuleNotFoundError: No module named 'pyproj'` → 没 `conda activate webgis`（W0 §1.2）；中文注释/输出乱码 → `chcp 65001`（坑 P7）；数值差几百公里 → 检查是不是漏了 `always_xy=True`（坑 P4）。

要点：
- **`always_xy=True`**：把输入按 (x=经度, y=纬度) 解释。不写它，某些 CRS 内部轴序是 lat/lon，结果数值完全错。
- **`TransformerGroup`**：PROJ 可能给出多条转换路径（精度不同、是否需要网格文件），打印 `description` 是排查跨版本差异的第一步。
- CRS 可以写 `EPSG:4326`、`4326`、`"OGC:CRS84"`——三种写法含义可能不同，**统一用 `EPSG:xxxx`**。

### 1.5 量算：为什么必须在 4326 + 椭球下算

墨卡托在每个纬度均匀放大 `1/cos(φ)`：

| 纬度 | 系数 `1/cos(φ)` | 3857 下量算偏差 |
| --- | --- | --- |
| 0°（赤道） | 1.0000 | 无 |
| 23.13°（广州） | 1.0874 | +8.7% |
| 39.91°（北京） | 1.3002 | +30% |
| 45°（哈尔滨） | 1.4142 | +41% |
| 60.5°（挪威） | 2.0308 | +103% |
| 85°（墨卡托上限） | 11.47 | +1047% |

**球面 vs 椭球**（另一层误差，别和上面混淆）：前端 `ol/sphere` 用正球，PostGIS `geography` 用 WGS84 椭球。北京–上海球面大圆 1068.51 km，椭球 1065.85 km，**差 2.66 km**。所以"前端测距和数据库不一样"通常不是 bug，是模型不同——说清口径即可。

### 练习 2：QGIS 里 4326 / 3857 量同一条线（周二~周三，最容易翻车）

**为什么做**：把"3857 会放大"从背来的结论变成自己量出来的数字（主计划 W1 练 2）。

**前置检查**：

- [ ] QGIS 能打开，版本 3.44.x
- [ ] **工程椭球已设为 WGS 84（EPSG:7030）**（见第 0 步，不设好后面全是假数据）
- [ ] [w1_test_features.geojson](../projects/coordinate-lab/w1_test_features.geojson) 存在

**第 0 步（决定成败，务必先做）**：`工程 → 属性 → 通用 → 测量 → 椭球`，改成 **`WGS 84 (EPSG:7030)`**。

> ⚠️ 这就是 week01.md 坑 **N9**：新建工程默认椭球是 **`None / Planimetric`**，此时字段计算器的 `$length` 退化成"坐标差 × 111319.491 米/度"的平面硬算，**结果显示为米但数值是错的**。
> 更阴的是：111,319.491 这个数**恰好等于**赤道 1 度经度在 3857 下的长度（都源于 `6378137 × π / 180`）。
> 所以看到 111,319.491 时，它既可能是"3857 平面距离"，也可能是"椭球设置丢失后的假距离"——**不能凭数值反推原因，必须去看工程属性里的椭球设置**。
> 三步定位法（值得记进方法论）：① 先用 `D:\xx\QGIS\bin\python-qgis-ltr.bat` 调 `QgsDistanceArea` 证明算法没错 → ② 查数据与半轴参数 → ③ 查工程级设置（问题就在这一层）。

**怎么做**（全程【QGIS 界面】）：

1. `图层 → 添加图层 → 添加矢量图层`，选 [w1_test_features.geojson](../projects/coordinate-lab/w1_test_features.geojson)（3 条线，声明 CRS84 = 4326，QGIS 自动识别）。
   - 预期现象：地图窗口出现三条线（两条在广州附近、一条在挪威）。
2. `工程 → 属性 → 坐标参考系` 设为 **EPSG:4326**；确认右下角状态栏 CRS 显示 `EPSG:4326`。
3. 打开属性表，用**字段计算器**（不是测量工具）新建/更新 Real 字段：

   ```
   length_wgs84_m  =  $length
   ```

   为什么用字段计算器：结果写进属性表，可复现、可导出、可截图；测量工具是临时的。
   - 预期现象：A 线算出约 **102,424.576**（看见 111,319.491 就是椭球没设，回第 0 步）。
4. 把工程 CRS 改成 **EPSG:3857**，再算一列 `length_3857_m = $length`。
   **每次切换 CRS 后先看右下角 CRS 显示**（坑 N11：工程 CRS 停在 3857 却以为在算 4326，会测出两个一模一样的值）。
   - 预期现象：A 线算出约 **111,319.491**——这次它是真的墨卡托平面距离。
5. 算膨胀率列 `ratio = length_3857_m / length_wgs84_m`，与理论 `1/cos(纬度)` 对比：

   | 线 | 位置 | 几何 | 4326+椭球（真实） | 3857（墨卡托） | 膨胀率 | 理论 `1/cos(纬度)` |
   | --- | --- | --- | --- | --- | --- | --- |
   | A | 广州 23.1291°N | 东西向 1° 经度 | 102,424.576 | 111,319.491 | +8.68% | 1.0874 |
   | B | 广州 23.5°N | 南北向 1° 纬度 | 110,751.075 | 121,389.472 | +9.61% | 1.0904 |
   | C | 挪威 60.5°N | 南北向 1° 纬度 | 111,420.728 | 226,085.310 | **+102.9%** | 2.0308 |

   （这是本仓库实测值，你的结果应与之一致；不一致就回头查椭球设置。）
6. 若必须用测量工具（画折线那种）：每量一条前先点 **`新建(N)`** 清空上一段（坑 N10：默认是连续折线模式，会把两条不相干的线连成一条跨洲长线，量出 7,970,465 m）。先在属性表选中要素按 `Ctrl+J` 飞到它，别在全局视野下瞎点。
7. 结论用自己的话写进 `notes.md`：**"同样是 1 个纬度，广州误差 8.7%，挪威误差 103%"**——面试被问"3857 什么时候不能用"，这就是你的答案。

**完成自查**：

- [ ] 三条线的膨胀率对上理论值（误差 <1 m，因为都是同一套 PROJ/GEOS 实现）
- [ ] 两张截图：椭球设置窗口 + 属性表两列长度值

## 6. W1 结束后的下一步预告（W2：空间数据格式与转换）

W2 你会从 [阿里 DataV.GeoAtlas](https://datav.aliyun.com/portal/school/atlas/area_selector) 下载家乡边界，用 `ogr2ogr` 瘦身到 100 KB 以内。**本周三个直接派上用场的东西**：

1. **`-t_srs` 的单位陷阱**：`-simplify 0.0005` 在 4326 下 ≈ 55 米，在 3857 下 ≈ 0.5 毫米。先想单位，再写数字——这是 1.1/1.5 节的结论。
2. **DataV 数据的坐标系口径存疑**（可能是 GCJ-02）：把边界叠到天地图，用练习 3 的方法**自己量出偏移量并下结论**，别信教程。
3. **`.prj` 丢失 = 三类原因之"类别二"**：W2 的 shapefile 会故意让你撞上它。

W2 前需要：QGIS 已装（含 **OSGeo4W Shell**，`ogr2ogr` 用它，别在 conda 里装 GDAL——week01.md 坑 N6：`GDAL_DATA` 未导出会报 `Cannot find header.dxf`）。
