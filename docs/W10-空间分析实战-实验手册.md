## 0. 本周要建立的三个认知

| # | 认知 | 为什么重要 |
| --- | --- | --- |
| 1 | **分析的起点是业务问题，不是工具**。"会画图"回答的是"哪里有什么"，"会分析"回答的是"该在哪建 / 谁受影响 / 够不够"——后者必须先翻译成可计算的子问题 | 甲方不为漂亮的地图付钱，为"这 3 个点该不该建食堂"付钱。四步法（拆解→指标→权重→叠加）是把玄学问题变成 SQL 的流水线 |
| 2 | **口径即生命**：任何一个缓冲区/距离/面积，先回答"在哪个坐标系、按什么几何模型算的"，再谈结果 | 4326 下 `ST_Buffer(geom, 500)` 会把 500 当**度**，画出一个跨半个地球的怪圈；3857 下算 500 米缓冲，广州直接多算 8.7%（你 W1 实测），面积级别约 +18%。数字"看起来正常"是空间分析里最危险的状态 |
| 3 | **结论的价值 = 可复现 + 诚实的局限**。没有局限声明的报告是不专业的，复现不了的报告在面试里等于零 | 主计划验收标准第三条专门考"你能否说出不确定性来自哪里"。数据是几年前的？人口是户籍还是常住？缓冲是直线还是真实路网？每一条都是别人挑战你结论的入口，先自己写出来 |

## 1. 学（约 5~6 小时，周一到周二）

### 1.0 术语速查（本周高频词的大白话版，先扫一遍再往下读）

**扫完你能做什么**：听到"缓冲区/权重/叠加/口径"不再发怵，能把每个词翻成一句大白话。

| 术语 | 大白话 + 类比 |
| --- | --- |
| 空间分析 | 用几何关系回答问题："谁在谁附近、谁跟谁重叠、到谁最近"——地图版的 Excel 筛选，只是条件是形状 |
| 选址分析 | 给一堆候选位置打分排队，选前三名。类比：找对象列出"距离单位<3km、身高…"逐项加权 |
| 缓冲区（buffer） | 以点/线/面为中心向外扩固定距离的"影响圈"。往池塘扔石头的水波纹，定死半径 500 m |
| 等时圈 | "从这点出发 N 分钟能到的范围"。真等时圈要算真实路网的绕行；简化版用直线距离×速度近似（口径必须声明，见 1.3） |
| 服务区/覆盖分析 | 一个设施能"管到"多少人口/小区——缓冲区 + 叠加统计的组合拳 |
| 适宜性评价 | 选址的近亲：不问"建哪 3 个点"，问"哪些地块适合做 X"（如绿地、电站），输出连续分级图 |
| 指标 / 权重 / 打分 | 指标=考核科目（人口覆盖）；权重=科目分值占比（0.35）；打分=按阈值给 1/3/5 分 |
| 叠加（overlay） | 多个条件图层叠在一起求交/求差，得到"同时满足"的区域——GIS 的看家动作，SQL 里就是 intersects + difference |
| 口径 | 一个数字背后"怎么算的"完整声明：坐标系、几何模型、统计年份、定义阈值。口径不清 = 耍流氓 |
| 敏感（性）分析 | 把权重/阈值故意改一改，看结论会不会翻车。会翻车的结论要如实标注 |

**常见误区（这张表读三遍）**：① 以为"缓冲区"天然是米——单位跟随 SRID（1.3 的全部内容）；② 以为"等时圈"画个圆就行——真实等时圈是路网算出来的不规则多边形；③ 以为权重是"客观算出来的"——权重是**人为设定**的，所以必须做敏感性分析；④ 以为 turf 和 PostGIS 结果理应一模一样——球面 vs 椭球，差异见 1.4。

### 1.1 思维转变：画图 vs 答题（0.5 h）

**学完你能做什么**：分清"交付一张图"和"交付一个结论"的差别，知道分析报告的评分标准是什么。

| 维度 | 会画图（W4~W9） | 会分析（本周起） |
| --- | --- | --- |
| 起点 | "把这份数据渲染出来" | "某个区该在哪 3 个位置建社区食堂？" |
| 对错标准 | 显示正确、配色好看、不卡 | 口径写清、中间结果可复现、结论敢标局限 |
| 交付物 | 一个网页 | 一份**有结论的报告** + 支撑它的脚本/SQL |
| 典型失败 | 图层不显示 | 用 3857 算缓冲多算了 8.7% 还没发现，结论错但没人知道 |

一句话记法：**画图是陈述句，分析是回答问题**。回答问题就有"题面、解法、验算"三件套——本周的模板全部围绕这三件套。

### 1.2 选址分析四步法：社区食堂案例完整走一遍（1.5 h）

**学完你能做什么**：把"选 3 个食堂位置"这句人话，亲手翻译成指标表、权重表、SQL 和结论图，且每个中间结果长什么样都见过。

概念四件套 · **四步法**：定义——问题拆解→指标→权重打分→叠加出图的分析流水线；类比——做饭：拆解=列菜单，指标=备料，权重=调味比例，叠加=下锅装盘；最小示例——本节全节就是；常见误区——跳过拆解直接写 SQL（方向错了越算越错）、权重不设理由（被人一问就崩）。

题面（主计划 W10 练习示例之一）：**为某区选 3 个社区食堂位置**。

**第一步 · 问题拆解**——把一句人话拆成可计算的子问题，每个子问题对应一条 SQL/turf 函数，并预览中间结果：

| 原始诉求 | 拆成的可计算问题 | 对应 SQL / turf 函数 | 中间结果长什么样 |
| --- | --- | --- | --- |
| "服务尽量多的老年人/小区" | 各小区常住人口排序 | `ORDER BY pop_resident DESC` | 一张小区名+人口表（示例见下） |
| "别和现有食堂抢生意" | 候选点到最近已有食堂的距离 ≥ 800 m | `ST_Distance(a::geography,b::geography)` / `turf.nearestPoint` | 候选点表多一列 `min_compete_dist`（米） |
| "步行能到" | 候选点 500 m 缓冲覆盖的小区数 | `ST_Buffer(...::geography,500)` + `ST_Intersects` / `turf.buffer`+`turf.intersect` | 候选点表多一列 `cnt_500m` |
| "临路但不贴路" | 距主干道 50~300 m 之间 | 双缓冲环带：`ST_Difference(缓冲300, 缓冲50)` | 一个环带面图层，QGIS 里半透明叠加 |
| "有合适的场地" | 底商/公共配套设施面要素 | 属性过滤 `WHERE type='底商'` | 候选点清单（几十个点位） |

中间结果示例（**示例数据，仅示意格式**——人口排序后的前 3 行）：

| name | pop_resident | min_compete_dist | cnt_500m |
| --- | --- | --- | --- |
| 示例·天河东小区 | 4200 | 1205 | 11 |
| 示例·员村新村 | 3100 | 860 | 8 |
| 示例·棠下花园 | 2600 | 640 | 9 |

**第二步 · 指标**——每个子问题变成一个字段：人口数、距最近食堂距离、500 m 内小区数、距最近主干道距离、可用场地面积。

**第三步 · 权重打分**——每指标归到 1~5 分，加权求和（权重和 = 1）。示例口径表（数字你要按自己的判断改，改动理由写进报告）：

| 指标 | 1 分 | 3 分 | 5 分 | 权重 |
| --- | --- | --- | --- | --- |
| 500 m 内小区常住人口 | <1000 | 1000~3000 | >3000 | 0.35 |
| 距最近已有食堂 | <500 m（太卷） | 500~800 m | >800 m | 0.25 |
| 距最近主干道 | >300 m（太偏） | 100~300 m | 50~100 m（临路不贴路） | 0.20 |
| 15 min 步行可达覆盖 | 小区少 | 中 | 多 | 0.20 |

**第四步 · 叠加出图**——把打分跑进 SQL（示意，表名换你自己的）：

```sql
-- 【容器内 psql】docker exec -it pgis psql -U postgres（先 \pset pager off，W0 坑 #7）
SELECT g.name,
       g.pop_in_500m,
       g.min_compete_dist,
       ( CASE WHEN g.pop_in_500m > 3000 THEN 5
              WHEN g.pop_in_500m >= 1000 THEN 3 ELSE 1 END * 0.35
       + CASE WHEN g.min_compete_dist > 800 THEN 5 ELSE 3 END * 0.25
       + CASE WHEN g.min_road_dist BETWEEN 50 AND 300 THEN 5 ELSE 1 END * 0.20
       )::numeric(4,2) AS total_score
FROM candidates g
ORDER BY total_score DESC
LIMIT 10;
```

**预期输出**：10 行 `name | pop_in_500m | min_compete_dist | total_score`，按总分降序。**失败时**：报 `column ... does not exist` → 中间表字段名与 SQL 不符，回第二步核字段；报 SRID 错 → 坑 P5。

分数前 10 拿回 QGIS / `webgis-starter` 分级设色出图（W5 技能回收），**候选点 + 500 m 缓冲 + 已有食堂**三个图层同屏——这就是"结论图"。

### 1.3 缓冲区 / 距离 / 等时圈的口径问题（1.5 h，本周硬核）

**学完你能做什么**：说出三种缓冲口径（4326 直接/3857 懒算/geography 或投影带）各自的单位与误差量级，并能在库里亲手把误差数字撞出来。

概念四件套 · **口径（buffer caliber）**：定义——缓冲半径"500"被解释成什么单位、在什么几何模型上算；类比——"一斤"在市斤秤和公斤秤上差一倍；最小示例——下面错误示范 vs 正确做法；常见误区——"3857 反正单位是米所以可以算"（广州 +8.7%，你 W1 实测）。

**错误示范**（想都别想）：

```sql
-- 【容器内 psql】geom 是 EPSG:4326 —— ST_Buffer 的第二参数单位跟随几何自己的 SRID，这里 500 = 500 度！
SELECT ST_Buffer(geom, 500) FROM residential;  -- 预期现象：画出一个能装下半个地球的圈（或超时）
```

度做单位的坐标系里要凑 500 米得写 0.0045 度左右——但纬度 1 度和经度 1 米数根本不等（广州 1 度经度 ≈ 102.4 km，1 度纬度 ≈ 110.8 km，你自己的 W1 实测数据），圆变成歪瓜裂枣。**结论：度单位下别做缓冲。**

**正确做法一：转投影坐标系算**（CGCS2000 国家基本比例尺分带 4523 系列，或广州用 UTM 49N = EPSG:32649）：

```sql
-- 【容器内 psql】4326 → 投影像米 → 缓冲 → 转回 4326 存储/发布
SELECT ST_Transform(
         ST_Buffer(ST_Transform(geom, 32649), 500),
         4326) AS buf_500m
FROM residential;
```

**正确做法二：geography 类型**（PostGIS 按椭球模型直接在地球上算米，小范围最省事）：

```sql
-- 【容器内 psql】
SELECT ST_Buffer(geom::geography, 500)::geometry AS buf_500m
FROM residential;
```

**预期输出（两种正确做法）**：返回的几何转 32649 算面积约 78.5 万 m²（π·500²）。**失败时**：报 `Unknown SRID` → 表没声明 SRID，坑 P5；面积数量级离谱 → 单位又混了，坑 P1/P6。

**偷懒做法（本周实验对象）**：转 3857 算。广州纬度 23.13°，Web 墨卡托长度膨胀系数 = 1/cos(23.13°) ≈ **1.0874**——这正是你 W1 在 QGIS 里实测的 +8.68%（[week01.md 第十四节](../notes/week01.md) A 线：真实 102,424.576 m vs 墨卡托 111,319.491 m）。半径多 8.7%，**缓冲圈面积就约多 (1.0874² − 1) ≈ 18.4%**。练习 3 就让你亲手把这两个数撞出来。挪威 60.5°N 膨胀 +103%，圈面积翻约 4 倍——"看起来都叫 Web 墨卡托米，误差却随纬度急剧恶化"，这就是不能偷懒的原因。

**距离/面积配套提醒**（W7 验收项回收）：4326 几何直接 `ST_Distance(a,b)` 结果是度不是米，直接 `ST_Area` 是"平方度"没有业务意义；统一走 `::geography` 或投影带，和上面同理。

**等时圈的口径**：完整等时圈要真实路网 + 绕行系数（OSM 路网 + pgrouting/OSRM，超出本周）。**简化口径**也允许做，但必须在报告里声明：按 75 m/min 步行速度 × 15 min = 1125 m 直线半径，再考虑实际绕行系数 1.3~1.6，等效直线缓冲常取 **700~850 m**——"我们用的是直线等效缓冲，不是真实路网等时圈"这句话写进局限，就是专业。

### 1.4 @turf/turf 前端轻量分析（1 h）

**学完你能做什么**：在浏览器 Console 里用 turf 算缓冲、求交、找最近点，并解释 turf 与 PostGIS 结果为什么差一点。

概念四件套 · **turf**：定义——浏览器端的轻量空间分析库；类比——装在浏览器里的迷你 QGIS 几何工具；最小示例——下面三段 Console 代码；常见误区——把它当"精确分析引擎"（它是交互级工具，批量精确分析回 PostGIS）。

**准备**：跑起 `webgis-starter`（【PowerShell】`npm install` → `npm run dev`，打开 <http://127.0.0.1:5173>），在【浏览器 DevTools】Console 里先加载 turf：

```js
// 【浏览器 DevTools Console】starter 页面。unpkg 不通就换 jsdelivr
const s = document.createElement('script');
s.src = 'https://unpkg.com/@turf/turf@7/turf.min.js';
document.head.appendChild(s);
// 预期现象：稍候输 turf 回车能补全即加载成功。
// 失败时：国内网络不稳先在 Steam++ 里确认 hosts 加速状态（W0 第六节）→ 仍不通记坑 P8 同款思路
```

**buffer**（500 米圆，turf 内部自动处理经纬度→米的换算）：

```js
// 【浏览器 DevTools Console】
const pt = turf.point([113.2644, 23.1291]);              // 广州，GeoJSON 顺序是 [经度, 纬度]
const buf = turf.buffer(pt, 500, { units: 'meters' });
console.log(turf.area(buf));                              // 预期输出：约 78~79 万（π×500²≈785,398）
```

**intersect**（缓冲圈与一个矩形地块求交，"受影响面积"的原型）：

```js
// 【浏览器 DevTools Console】
const a = turf.buffer(turf.point([113.2644, 23.1291]), 500, { units: 'meters' });
const b = turf.polygon([[[
  [113.258, 23.124], [113.270, 23.124], [113.270, 23.135],
  [113.258, 23.135], [113.258, 23.124]
]]]);
const part = turf.intersect(turf.featureCollection([a, b]));  // v7 入参是要素集
console.log(part ? turf.area(part).toFixed(0) + ' m²' : '不相交');  // 预期输出：几十万 m² 的一行
```

**nearestPoint**（候选点到最近已有食堂——四步法里"竞争距离"指标的前端版）：

```js
// 【浏览器 DevTools Console】
const fs_ = turf.featureCollection([
  turf.point([113.250, 23.120], { name: 'A食堂' }),
  turf.point([113.280, 23.140], { name: 'B食堂' })
]);
const q = turf.point([113.2644, 23.1291]);
const near = turf.nearestPoint(q, fs_);
console.log(near.properties.name, turf.distance(q, near, { units: 'meters' }).toFixed(0));
// 预期输出：'A食堂'，距离约 1.7 km——和你在地图上目测的方向一致吗？
```

**失败时（三段通用）**：`turf is not defined` → 上一步 script 没加载完，等两秒重试；结果数量级离谱 → 检查坐标顺序是不是 [经度, 纬度] 写反了。

**turf 的口径声明要写进报告**：turf 的距离/面积用**球面模型**（半径 6371008.8 m），PostGIS `geography` 用 **WGS84 椭球**——你 W1 实测过两者口径差：北京–上海球面 1068.51 km vs 椭球 1065.85 km，差约 2.66 km。小范围 500 m 分析两者差异在厘米~分米级，可接受，但"前端 turf 与库内 geography 结果不完全一致是正常的，因为一个球一个椭"必须能解释（这本身就是面试答案）。

**正式项目里怎么用 turf**：Console 试跑是学习姿势；工程做法是 `npm i @turf/turf` 后 `import * as turf from '@turf/turf'`，打包进 Vite 项目。分工原则（写进报告方法节）：**批量/精确分析在 PostGIS（有索引、可复现），前端 turf 只做交互级即时计算**（画个临时缓冲、点击算最近点），两头别用错地方。

### 1.5 报告写法：数据来源 / 口径 / 局限（0.5 h）

**学完你能做什么**：照可填空骨架写出一份 2 页报告，每节知道"写什么、不写什么"。

2 页分析报告的**可填空骨架**（练习 5 直接复制成 `README.md` 填空，每节给"✍ 写什么 / ✗ 不写什么"）：

```markdown
# 某区社区食堂选址分析报告（2026-12）

## 1. 问题
> ✍ 写什么：一句业务问题 + 拆解后的可计算子问题清单 + 期望输出形式（3 个候选点位）
> ✗ 不写什么：背景宏大叙事、与选址无关的区情介绍

## 2. 数据
> ✍ 写什么：每张表一行——来源 / 获取日期 / 版本年份 / 坐标系 / 口径(常住 or 户籍、GCJ-02 or WGS84) / 已知问题
> ✗ 不写什么："数据来自网络"这种无法复核的表述

## 3. 方法
> ✍ 写什么：四步法各一段——指标定义、打分阈值与权重（含权重理由）、**缓冲口径声明**
>   （geography 椭球 or 投影带，500 m 缓冲；等时圈用直线等效 800 m，非真实路网）、
```

### 练习 3：缓冲口径实验（周三，本周必须留档的"自证数据"）

**为什么做**：把 1.3 的 "+8.7% 不是道听途说"变成你**本周场景下**的实测数，报告方法节的口径声明就有自己的证据。

**前置检查**：

- [ ] 能进 pgis 的 psql（W0 坑 #7：先 `\pset pager off`）

**编号步骤**：

1. 挑一个真实点（如广州塔），分别生成三种 500 m 缓冲并存表【容器内 psql】：

   ```sql
   -- 先建一个单点表
   CREATE TABLE pt (name text, geom geometry(Point, 4326));
   INSERT INTO pt VALUES ('广州塔', ST_SetSRID(ST_MakePoint(113.2644, 23.1291), 4326));

   -- 三种口径各生成一个 500 m 缓冲，存一张实验表
   CREATE TABLE buffer_caliber AS
   SELECT 'lazy_3857' AS method,
          ST_Transform(ST_Buffer(ST_Transform(geom, 3857), 500), 4326) AS g
   FROM pt
   UNION ALL
   SELECT 'utm_32649',
          ST_Transform(ST_Buffer(ST_Transform(geom, 32649), 500), 4326)
   FROM pt
   UNION ALL
   SELECT 'geography',
          ST_Buffer(geom::geography, 500)::geometry
   FROM pt;
   ```
   （写不顺就分三条 `SELECT ... ;` 逐个跑、结果截图，效果一样。）
2. 对比三个圈的面积（**面积必须转投影带算**，4326 上 `ST_Area` 是"平方度"没有业务意义——坑 P6）：

   ```sql
   SELECT method,
          ROUND(ST_Area(ST_Transform(g, 32649))::numeric) AS area_m2
   FROM buffer_caliber;
   ```

   **预期输出**：三行，geography 与 utm_32649 接近 785,398，lazy_3857 大约 93 万（+18% 附近）。**失败时**：三行一样 → 检查 SQL 是否真用了三种口径；报错 → 坑 P1/P5。
3. 回答：`lazy_3857` 的面积比 `geography` 大几个百分点？接近你预测的 +18.4% 吗（长度 +8.7% 平方而来）？把三个数和偏差率写进报告方法节。
4. 口径错误直观感受：单独跑一次 `SELECT ST_Buffer(geom, 0.0045) FROM pt;`（把 500 m 当 0.0045 "度"凑），转 3857 后用 QGIS 量这个"圆"的南北轴与东西轴长度——两者不等，因为 1 度经度 ≠ 1 度纬度的米数（广州 102.4 km vs 110.8 km，你 W1 实测），圆被拉成歪椭圆。

**完成自查**：

- [ ] 有一张自测的口径对比表（三行面积 + 偏差率）
- [ ] 报告里"本文缓冲采用 geography（WGS84 椭球）"这样的句子每个词都有依据
